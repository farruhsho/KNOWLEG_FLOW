# Контент-пайплайн ORT Master KG (`tools/content_pipeline`)

Офлайн-инструмент (Node 22 + TypeScript), который превращает структуру ОРТ 2026
(`assets/data/exam_blueprints.json`) и каталог тем школьной программы КР в
банк **оригинальных** заданий и собранные по blueprint варианты, а затем
импортирует их в Firestore (`knowleg-33f36`). Реализует ARCHITECTURE §7.
Схемы документов — ARCHITECTURE §1.2–1.3 (snake_case), см. `src/schema.ts` и
экспорт `content/schema/*.schema.json`.

Каждый этап — отдельная подкоманда, читает и пишет JSON под `content/`.
Поэтому любой батч можно прервать и продолжить, а результат — проверить в
git-диффе до импорта.

```
matrix → generate → verify → translate-check → dedup → assemble → timing → validate → import → registry
            (платно)  (платно)  (структура бесплатно,                         (dry run по умолчанию)
                                 API — платно)
```

## 0. Установка и проверка

```bash
cd tools/content_pipeline
npm install
npm run typecheck      # tsc --noEmit
npm test               # node:test, без сети и без ключей
npm run cli -- help    # список этапов и флагов
```

Все пути во флагах — относительно корня репозитория (`--root` переопределяет).

### Раскладка данных

| Путь | Что | В git |
|---|---|---|
| `content/curriculum/topics.json` | Каталог тем: предметы → темы → подтемы, классы школьной программы КР, веса тем в частях blueprint (`slots`) | да |
| `content/matrix/<blueprint>.json` | Матрица тем × сложность на один вариант (этап 1) | да |
| `content/bank/<batch>/items.json` | Банк заданий (`BankFile`): тексты, вопросы, ключи, журнал проверок | да |
| `content/bank/<batch>/batch.json` | Журнал платного прогона: модель, аргументы, токены, стоимость | да |
| `content/variants/<blueprint>/<lang>/v_*.json` | Собранные варианты (`VariantFile`) | да |
| `content/schema/*.schema.json` | JSON Schema документов (генерируется `schemas`) | да |
| `content/registry.json`, `content/REGISTRY.md` | Реестр готовности (этап 10) | да |
| `content/reports/` | `dedup.json`, `import-plan.json`, `import-report.json` — пересоздаются при каждом запуске | нет |
| `content/external/` | Read-only выгрузки существующего контента для `dedup --against` | нет |
| `content/bank/sample/items.json` | 16 рукописных оригинальных заданий (12 ru + 4 перевода ky), `draft`, фикстуры тестов | да |

Идентификаторы детерминированы и основаны на содержимом: `q_<20 hex>` =
начало `sha256` публичных полей вопроса (язык, тип, условие, варианты,
таблица, имя файла картинки, текст), `p_<20 hex>` — то же для текста,
`tg_…` — группа переводов, `v_<blueprint>_<lang>_<NNN>` — вариант. Любая
правка публичного текста даёт новый id (старый документ в Firestore остаётся,
пайплайн ничего не удаляет). После ручной правки файла банка:
`npm run cli -- lint --fix` пересчитывает хэши и id.

Статусы заданий (`review.status`): `draft` → `ai_verified` →
`methodologist_approved`, либо `rejected`. Пайплайн **никогда** не ставит
`methodologist_approved` сам — только человек (команда `review` с `--by <uid>`
или админка + `review-sync`).

## 1. Этапы

### 1.1 `matrix` — матрица тем и сложности

```bash
npm run cli -- matrix                       # все blueprints
npm run cli -- matrix --blueprint ort_main_2026
```

Для каждого blueprint × язык × раздел × часть: целевое число заданий темы в
одном варианте (`target`, допустимый диапазон `min..max`), точные числа по
сложности из `difficulty_mix` (30/50/20 → 9/15/6 для 30 заданий) и разбиение
тема × сложность с согласованным округлением (строки = цели тем, столбцы =
числа по сложности). Тексты чтения: 2 самостоятельных + 1 парный, по 10
вопросов. Темы грамматики берутся по языку варианта (`grammar_ru.*` /
`grammar_ky.*`, 6 типов заданий blueprint). Веса тем в каталоге — рабочая
версия автора; **методист проверяет их до массовой генерации**.

### 1.2 `generate` — генерация (платно, по явному согласию)

```bash
# только план и оценка стоимости (без API):
npm run cli -- generate --blueprint ort_main_2026 --language ru --variants 10 --plan
# реальный прогон (ключ — только в окружении оператора):
export ANTHROPIC_API_KEY=...        # никогда не коммитить, никогда не класть в приложение
npm run cli -- generate --blueprint ort_main_2026 --language ru --section math --part math_comparison \
  --variants 10 --per-request 5 --max-items 200 --max-cost-usd 15 --i-understand-this-costs-money
# переводы ru → ky уже проверенных заданий:
npm run cli -- generate --blueprint ort_subject_chemistry_2026 --language ky --translate-from ru \
  --max-items 100 --i-understand-this-costs-money
```

* Без `--i-understand-this-costs-money` команда только печатает дефицит по
  ячейкам (раздел, часть, тема, сложность, язык) и оценку стоимости.
* Модель — `CONTENT_MODEL` (по умолчанию `claude-opus-5-5`), глубина —
  `CONTENT_EFFORT` (по умолчанию `high`); `temperature/top_p/top_k` не
  передаются. Ответ строго по JSON Schema (`output_config.format`), затем
  повторная проверка zod. Включён серверный fallback при отказе модели
  (`fallbacks: "default"`), отключается `--no-fallbacks`.
* Промпт запрещает копировать, переводить и перефразировать задания ЦООМО /
  testing.kg, Secom, ORTPREP и других издателей; требует единственный верный
  ответ, правдоподобные дистракторы с описанием типичной ошибки
  (`wrong_option_notes`), пошаговое объяснение, основание в школьной
  программе (`source.basis`). Для «сравнения величин» варианты ответов —
  фиксированные варианты blueprint (модель пишет только условие и две
  колонки).
* Все новые задания — `draft`, `source.kind = original`. Банк сохраняется
  после каждого запроса: повторный запуск той же команды продолжит с места
  остановки. `--max-cost-usd` останавливает прогон по фактическим токенам.

### 1.3 `verify` — независимая проверка

```bash
npm run cli -- verify --local-only                                # бесплатно: только пересчёт арифметики
npm run cli -- verify --batch gen_ort_main_2026_ru_2026-11-10 --i-understand-this-costs-money
```

Отдельный запрос решает задание **вслепую** (без ключа и объяснения) и
проводит аудит: однозначность, несколько верных / ни одного верного,
фактические ошибки, соответствие программе, риск копирования, качество
языка (для кыргызского — ң ө ү и естественность). Для математики локальный
точный вычислитель (рациональные числа, `\frac`, `\sqrt`, степени, проценты
«p % от n» / «n санынын p пайызы») пересчитывает ответ, если условие —
чистая арифметика; символьные задания он не угадывает. Итог: `ai_verified`,
если слепой ответ совпал с ключом, нет блокирующих замечаний и арифметика
сошлась; иначе `rejected` с причинами в `review.notes`. Одобренные и
отклонённые людьми задания не меняются (если слепой решатель с одобренным
заданием не согласен, команда об этом сообщает). Модель проверки —
`VERIFY_MODEL` (по умолчанию как `CONTENT_MODEL`); для независимости ошибок
можно поставить другую модель.

### 1.4 `translate-check` — согласованность переводов

```bash
npm run cli -- translate-check                                    # структура, бесплатно
npm run cli -- translate-check --api --i-understand-this-costs-money
```

Для пар ru ↔ ky с общим `translation_group_id`: тип, число вариантов, ключ,
сложность, тема, слот blueprint, форма таблицы, все числа и формулы
`$…$`, связь текстов. `--api` добавляет двуязычную смысловую проверку.
Задания с `translate_check.status = failed` не попадают в сборку.

### 1.5 `dedup` — дубликаты

```bash
npm run cli -- export-existing --collection questions          # read-only выгрузка старой базы в content/external/
npm run cli -- dedup --threshold 0.85 --against content/external/questions.json --mark
```

Нормализация сохраняет кириллицу и **не** сводит ң ө ү к н о у («төрт» ≠
«торт»); похожие символы (ӊ ӧ ӱ, латинские ö ü, латинская «а» внутри
кириллического слова) приводятся к каноническим. Точные дубли — по хэшу
нормализованного текста, близкие — по Жаккару 5-символьных шинглов
(для больших групп — MinHash LSH). Сравнение внутри языка; вопросы к текстам —
только внутри своего текста; языковые версии одной группы перевода между
собой не сравниваются. Отчёт — `content/reports/dedup.json` (кластеры).
`--mark` пишет в задания `pipeline.dedup`: в сборку идёт только канонический
член кластера (самый проверенный, затем самый старый), а совпадения с
существующим контентом исключаются.

### 1.6 `assemble` — сборка вариантов

```bash
npm run cli -- assemble --blueprint ort_main_2026 --language ru --count 5
npm run cli -- assemble --blueprint ort_main_2026 --language ky --numbers 1-5 --allow-unapproved   # черновики
```

Из одобренных заданий (с `--allow-unapproved` — также `ai_verified`; `draft`
и `rejected` — никогда) собирается вариант, точно совпадающий с blueprint:
число заданий в каждом разделе и части, матрица тем (сначала точные ячейки
тема × сложность, затем точные итоги, затем диапазоны тем), распределение
сложности, раскладка текстов (чтение: 2 самостоятельных + 1 парный текст по
~10 вопросов, вопросы текста идут подряд). Задание не повторяется в
вариантах одного blueprint + язык, если не указан `--allow-reuse`.
Опубликованный и снятый с публикации (`archived`) вариант не пересобирается:
id снятого варианта остаётся занятым в Firestore, для замены берётся новый
номер. Сборка детерминирована
(`--seed`, по умолчанию `blueprint|язык|номер`). Каждый вариант сразу
проходит `validate` и `timing`, результаты пишутся в `assembly`.

### 1.7 `timing` — контроль времени

```bash
npm run cli -- timing --blueprint ort_main_2026 --margin 0.1
```

Оценка времени решения по типу, предмету, сложности и длине задания плюс
чтение текстов (≈ 150–180 слов/мин, ×1,2 на возвраты к тексту). Раздел
«влезает», если оценка ≤ длительность × (1 − запас). Константы —
калиброванная стартовая точка (стандартный вариант любого blueprint
укладывается с запасом 10 %); после появления реальных попыток их нужно
заменить медианами из `exam_attempts`.

### 1.8 `validate` — финальная проверка набора вариантов

```bash
npm run cli -- validate --blueprint ort_main_2026 --publish --require-languages
```

Те же правила, что у `adminPublishVariant` (`src/validate.ts` не зависит от
файловой системы и Firestore, его можно переиспользовать в функции): схема
`exam_variants`, версия blueprint, разделы в порядке blueprint, число
заданий в разделе и по типам, фиксированные варианты «сравнения величин»,
наличие ключа и корректность буквы ключа, статусы (для публикации — все
`methodologist_approved`, `rejected` блокирует всегда), дубли id и
содержимого, язык заданий и текстов, связность вопросов к тексту, раскладка
текстов. По набору: повтор заданий между вариантами, дубли номеров, наличие
всех языков blueprint (`--require-languages` делает это ошибкой).
Предупреждения (не блокируют): отклонение от матрицы, перекос букв ключа,
черновики.

### 1.9 `import` — запись в Firestore

```bash
npm run cli -- import --blueprint ort_main_2026                     # DRY RUN: только план
export GOOGLE_APPLICATION_CREDENTIALS=/path/outside/repo/sa.json      # или gcloud auth application-default login
npm run cli -- import --blueprint ort_main_2026 --commit
npm run cli -- import --blueprint ort_main_2026 --publish --published-by <uid> --commit
```

* По умолчанию — **dry run**: план записей в `content/reports/import-plan.json`.
  Запись — только с `--commit`; батчи ≤ 400 операций; **удалений нет**.
  Перед записью читаются все целевые документы; итог коммита — в
  `content/reports/import-report.json`.
* Коллекции: `exam_blueprints` (документ blueprint целиком), `exam_passages`,
  `exam_questions` (публичные поля §1.3 без ключа + `part_id` + `pipeline_hash`
  + `pipeline_translation_group_id`),
  `exam_question_keys`, `exam_variants`. Id идемпотентны (по хэшу содержимого):
  повторный импорт ничего не дублирует, документы без изменений не
  перезаписываются.
* **Таблицы.** Firestore не хранит массив внутри массива, поэтому
  `exam_questions.table` хранится как
  `{"headers": ["…"], "rows": [{"cells": ["…", "…"]}]}`. В банке, во всех
  этапах и в хэше содержимого остаётся `rows: [["…", "…"]]`; форма меняется
  только при записи. Cloud Functions отдают клиенту `rows: [[…]]`. План с
  массивом внутри массива (в любом документе) не строится: ошибка на этапе
  dry run, а не посреди коммита.
* **`part_id`.** Каждый вопрос получает `part_id` из слота blueprint
  (`target.part_id`): по нему админка фильтрует банк и автозаполняет части
  варианта. В хэш содержимого поле не входит, id не меняются; повторный
  импорт дописывает его в старые документы.
* **Статус варианта.** Новый вариант пишется как `draft`; `published` — только с
  `--publish` и только если все его задания `methodologist_approved` и у всех
  есть ключ. Статус варианта, **который уже есть в Firestore, пайплайн не
  меняет никогда** (`status`, `published_at`, `published_by` не пишутся):
  публикует и снимает с публикации существующий вариант только
  `adminPublishVariant` (админка). `import --publish` для такого варианта
  печатает «publish in the admin panel». Опубликованный или снятый с
  публикации (`archived`) вариант пайплайн не трогает вовсе; `stats` и
  `created_at` не перезаписываются. Локальный файл варианта помечается
  `published` только если вариант создан этим запуском как опубликованный.
* **Правки вне пайплайна (админка, консоль).** Пайплайн пишет в вопрос
  `pipeline_hash` (= записанный `content_hash`) и
  `pipeline_translation_group_id` (= записанная связь переводов), в ключ —
  `pipeline_hash` ключа, в текст — `content_hash` и `pipeline_hash`, в
  вариант — хэш своих полей. Документ считается изменённым вне пайплайна, если: задан
  `edited_in_cms_at` (админка ставит его при сохранении вопроса); его
  `content_hash` не совпадает с `pipeline_hash`; публичные поля не совпадают с
  `content_hash` (правка в консоли); у ключа, текста или варианта-черновика
  есть `updated_by` (сохранён в админке) или поля не совпадают с
  `pipeline_hash`. Такой документ **не перезаписывается**, если его
  содержимое отличается от банка: он попадает в `cms_conflicts` (вывод CLI и
  `import-report.json`). Вопрос и его ключ — одно целое: конфликт любого из
  них оставляет как есть оба. Новый вариант, в котором есть такие вопросы
  или тексты (или вопросы, отклонённые в Firestore), пишется как `draft`, а
  не `published` (`publish_blocked`).
  Разрешение конфликта: (а) перенести правку в банк (git; `lint --fix`,
  если изменился публичный текст — тогда у задания будет новый id, и вариант
  нужно пересобрать), после чего содержимое совпадёт и конфликт исчезнет;
  или (б) `import … --commit --overwrite` — вернуть содержимое банка
  (правка в Firestore теряется, поле `edited_in_cms_at` удаляется).
  `--overwrite` никогда не меняет статус варианта и не трогает
  опубликованные и снятые варианты.
* **Правка из админки уже в банке (`cms_caught_up`).** Если у вопроса задан
  `edited_in_cms_at`, а его содержимое по схеме хэша пайплайна (язык, тип,
  условие, варианты ответа, таблица, картинка, текст; метаданные вроде
  `topic_id`, `difficulty`, `part_id`, `source` не учитываются) совпадает с
  банком — правку перенесли в git, или сохранение в админке меняло только
  ключ или метаданные, — это не конфликт. Импорт «забирает» документ
  обратно: пишет только `pipeline_hash` (и `content_hash`, если там чужой
  хэш) и удаляет `edited_in_cms_at` (`FieldValue.delete()`); содержимое и
  метаданные на этом шаге не меняются. Иначе метка осталась бы навсегда, и
  любое следующее изменение метаданных в банке (тот же id) считалось бы
  конфликтом вопроса и его ключа до глобального `--overwrite`. В отчёте
  (`cms_caught_up`) для каждого такого вопроса перечислены `pending_fields` —
  поля, которые ещё отличаются от банка (например, `difficulty`, изменённая
  в админке): **следующий импорт запишет в них значения банка**, поэтому их
  нужно перенести в банк, если правка из админки должна остаться. Ключ при
  этом проверяется как обычно: если ключ, исправленный в админке, ещё не
  перенесён в банк, вопрос и ключ остаются конфликтом и метка не снимается.
* **Связи переводов (`translation_links_kept`).** `translation_group_id`
  принадлежит админке, как только его там изменили (создать перевод,
  связать, отвязать — эти действия не ставят `edited_in_cms_at`). Пайплайн
  помнит, какую связь он записал (`pipeline_translation_group_id`), и не
  перезаписывает `translation_group_id`, который отличается и от неё, и от
  банка: связь остаётся как в Firestore, вопрос (кроме связи) пишется как
  обычно, а сама связь попадает в `translation_links_kept` (вывод CLI и
  `import-report.json`; вариант из-за этого не блокируется). У документов,
  записанных до появления `pipeline_translation_group_id`, сохраняется любая
  непустая связь, отличная от банка (кто её поставил, уже не узнать);
  совпадающая с банком связь просто дописывает это поле. Как разрешить:
  записать ту же связь в банк (`translation_group_id`) — тогда пайплайн
  снова владеет связью; или `import … --commit --overwrite` — вернуть связь
  из банка (попадает в `overwritten`).
* Если в Firestore статус вопроса дальше по цепочке (методист одобрил в
  админке) или `rejected`, он сохраняется; `review-sync` переносит такие
  решения в локальный банк (только чтение Firestore) — но только для вопросов,
  чьи вопрос и ключ не менялись вне пайплайна (правка, уже совпадающая с
  банком, и изменённая в админке связь переводов этому не мешают).

### 1.10 `registry` — реестр готовности

```bash
npm run cli -- registry
```

`content/registry.json` и `content/REGISTRY.md` считаются только из файлов
банка и вариантов. Две таблицы: по blueprint × язык (цель 100 вариантов:
собрано, ai_verified, одобрено, опубликовано; задания по статусам) и по
направлениям (номер варианта N засчитывается, только если N одобрен /
опубликован на **всех** языках направления; цель 100 × 10 = 1000). Вариант
считается «одобренным», только если все его задания `methodologist_approved`.

### Служебные команды

| Команда | Что делает |
|---|---|
| `lint [--fix]` | Схема, хэши, id, ключи, тексты, группы переводов, темы из каталога; `--fix` пересчитывает хэши после ручной правки |
| `review --ids … --status methodologist_approved\|rejected --by <uid> [--notes …] [--from-draft]` | Решение методиста в файлах банка (одобрить `draft` без AI-проверки — только явно, `--from-draft`) |
| `review-sync` | Читает из Firestore решения админки: `exam_questions.review` → банк (кроме вопросов и ключей, изменённых в админке), статус `archived` / `published` варианта (`adminPublishVariant`) → `content/variants` |
| `export-existing [--collection questions]` | Read-only выгрузка существующей коллекции для `dedup --against` |
| `schemas` | Обновляет `content/schema/*.schema.json` |

## 2. Стоимость генерации на 1 000 заданий

Цены (USD за 1 млн токенов, вход / выход): `claude-opus-5-5` $4 / $20,
`claude-sonnet-5-5` $2 / $10, `claude-haiku-5-5` $0,10 / $0,50.

Допущения (те же, что в оценке, которую печатает CLI; токены «размышлений»
модели входят в выходные токены):

| Шаг | Вход, ток./задание | Выход, ток./задание | Комментарий |
|---|---:|---:|---|
| generate | 440 | 1 200 | 5 заданий в запросе: ~2 200 вход (системный промпт + спецификация + список «не повторять»), ~900 на задание + 1 500 на запрос |
| verify | 1 500 | 2 500 | одно задание — один слепой запрос |
| generate --translate-from | 1 800 | 1 600 | перевод задания, объяснения и заметок |
| translate-check --api | 2 500 | 800 | на пару |
| Брак | | | генерация с запасом 30 % (`--overgeneration 1.3`), проверяется всё сгенерированное; переводы — 10 % повторов |

Тексты для чтения дешевле в пересчёте на задание (один запрос — текст и
~12 вопросов), поэтому оценка для них завышена. Кэш промптов не учитывается
(системные промпты короче минимального кэшируемого префикса), стоимость
кэш-чтений в журнале считается по полной цене входа — то есть журнал даёт
верхнюю границу. Реальный расход токенов «размышлений» может отличаться в
1,5 раза в обе стороны: **первый пилотный батч нужен, чтобы измерить** —
фактические токены и стоимость пишутся в `content/bank/<batch>/batch.json`.

| На 1 000 **принятых** заданий | Opus 5.5 | Sonnet 5.5 | Haiku 5.5 |
|---|---:|---:|---:|
| Оригиналы: generate + verify, ×1,3 | ≈ $106 | ≈ $53 | ≈ $2,7 |
| Переводы: translate + verify + translate-check, ×1,1 | ≈ $133 | ≈ $67 | ≈ $3,3 |

Расчёт для Opus: generate 1 000 × (440 × 4 + 1 200 × 20) / 10⁶ = $25,8;
verify 1 000 × (1 500 × 4 + 2 500 × 20) / 10⁶ = $56,0; (25,8 + 56,0) × 1,3 ≈ $106.
По умолчанию используется `claude-opus-5-5`; выбор более дешёвой модели —
решение владельца (качество кыргызского текста и точность ключей нужно
сравнить на пилоте; Haiku для генерации заданий ОРТ не рекомендуется).

## 3. Проверка методистом (обязательный шаг)

Опубликовать вариант можно только если **все** его задания имеют статус
`methodologist_approved` (ARCHITECTURE §1.3). AI-проверка этот статус не
ставит.

**Кто одобряет.** Право `review_questions` — роли `methodologist` и
`super_admin` (ARCHITECTURE §2). `content_manager` может редактировать и
публиковать, но не одобрять. Правило двух лиц: оператор пайплайна и
одобряющий методист — разные люди. Задания на кыргызском одобряет методист —
носитель кыргызского языка; предметные — учитель предмета.

**Как.** (а) В админке: `import --commit` загружает задания (`ai_verified`) и
варианты-черновики, методист одобряет или отклоняет, затем `review-sync`
переносит решения в банк. Варианты, которые уже есть в Firestore,
публикуются в админке (`adminPublishVariant` повторяет проверки на сервере);
`review-sync` переносит их статус в `content/variants`. Если методист
исправил в админке текст или ключ, задание попадает в `cms_conflicts` при
следующем импорте: правку нужно перенести в банк (см. §1.9). (б) В git:
методист проверяет файлы банка и выполняет
`review --ids … --status methodologist_approved --by <uid>` (изменения
проходят ревью pull request). Затем `assemble` → `validate --publish` →
`import --publish --commit` — так публикуются варианты, которых ещё нет в
Firestore.

**Чек-лист методиста** (каждое задание):

1. Решить самостоятельно, не глядя на ключ; ответ совпадает с ключом.
2. Верный вариант ровно один, остальные однозначно неверны; нет «все
   перечисленные / ни один из перечисленных», двойных отрицаний, ловушек на
   формулировке.
3. Дистракторы правдоподобны, каждый соответствует типичной ошибке;
   `wrong_option_notes` описывают эти ошибки верно.
4. Объяснение и шаги решения верны, последовательны и понятны выпускнику.
5. Содержание в рамках школьной программы КР; `source.basis` (класс, тема),
   тема, подтема и сложность 1–3 размечены верно.
6. Язык: русский — литературная норма; кыргызский — естественный
   литературный язык с ң ө ү и терминологией школьных учебников, не калька с
   русского.
7. Формат части: «сравнение величин» — фиксированные варианты blueprint, D
   («информации недостаточно») только когда соотношение действительно зависит
   от неизвестных; аналогии — тип отношения однозначен; дополнение —
   пропуски «____»; тексты — ответ следует только из текста, факты в тексте
   верны или явно художественные.
8. Оригинальность: задание не похоже на известные задания ЦООМО / testing.kg,
   Secom, ORTPREP, сборников и сайтов; при сомнении — `rejected`.
9. Этичность: нет дискриминации, политической или религиозной агитации,
   травмирующих сюжетов; имена и реалии нейтральны и уместны.
10. Для перевода: смысл, числа, формулы и ключ совпадают с оригиналом.

## 4. Юридические правила

* В банк попадают **только оригинальные** задания (`source.kind = original`)
  или материалы, на которые есть письменная лицензия (`source.kind =
  licensed`, в `basis` — реквизиты лицензии). Схема не допускает иных
  значений.
* Задания ЦООМО (testing.kg, брошюры, демо-тесты, прошлые варианты), Secom,
  ORTPREP, других компаний, сборников и сайтов **не копируются, не
  переводятся и не перефразируются**. Из официальных материалов берётся
  только общедоступная структура теста (разделы, число заданий, время,
  формат ответов) — `exam_blueprints.json`. Промпт генерации прямо запрещает
  копирование; `dedup --against` сравнивает банк с существующей базой; при
  совпадении задание исключается.
* Сгенерированные и собранные варианты **никогда не выдаются за
  официальные**: не используются слова «официальный», «реальный вариант
  ОРТ», логотипы ЦООМО; результат всегда с пометкой «Учебный результат, не
  официальный балл ОРТ» (`scoring.disclaimer` в blueprint).
* Ключ Anthropic — только в окружении оператора (`ANTHROPIC_API_KEY`), ключ
  сервисного аккаунта Firebase — вне репозитория
  (`GOOGLE_APPLICATION_CREDENTIALS`). В клиент и в git секреты не попадают.
* Выгрузки существующего контента (`content/external/`) и отчёты
  (`content/reports/`) в git не коммитятся.

## 5. План батчей: 100 вариантов × 10 направлений

Цель — 100 номеров вариантов в каждом из 10 направлений (1 000 номеров).
Один документ `exam_variants` — один язык, поэтому номер N двуязычного
направления — это две языковые версии. Без повторов заданий внутри
blueprint + язык нужно:

| Направление | Языки | Заданий в варианте | Заданий на язык (×100) | Всего |
|---|---|---:|---:|---:|
| `ort_main_2026` | ru, ky | 150 | 15 000 | 30 000 |
| `ort_subject_{chemistry,biology,physics,math,history}_2026` | ru, ky | 40 | 4 000 | 5 × 8 000 = 40 000 |
| `ort_subject_english_2026` | en | 50 | 5 000 | 5 000 |
| `ort_subject_kyrgyz_lit_2026` | ky | 40 | 4 000 | 4 000 |
| `ort_subject_russian_lit_2026` | ru | 40 | 4 000 | 4 000 |
| `ort_state_language_2026` | ky | 50 | 5 000 | 5 000 |
| **Итого** | | | | **88 000** |

Из них переводами ru → ky можно получить ≈ 27 500 (математика и, частично,
аналогии/дополнение основного теста; предметные тесты). Тексты для чтения и
грамматика основного теста на кыргызском, а также кыргызские направления
пишутся сразу на кыргызском (≈ 60 500 оригиналов всего).

**Деньги (оценка, Opus 5.5):** 60 500 × $0,106 + 27 500 × $0,133 ≈ $10 100
(Sonnet 5.5 — ≈ $5 050). Уточняется по итогам пилота.

**Пропускная способность API (оценка, не измерена).** CLI работает
последовательно: запрос генерации на 5 заданий — ~1–3 мин, слепая проверка
одного задания — ~0,5–1 мин. Один процесс: ~100–300 сгенерированных или
~60–120 проверенных заданий в час. Можно запускать несколько процессов
параллельно на разные `--section/--part` с разными `--batch-id` (отдельные
файлы банка), в пределах лимитов API-аккаунта. Всего с запасом: ≈ 79 000
оригиналов (≈ 16 000 запросов генерации), ≈ 30 000 переводов и ≈ 109 000
слепых проверок — ≈ 2 400 процессо-часов, то есть при 8 параллельных
процессах порядка 2–4 недель машинного времени; узкое место — проверка.

**Реальное узкое место — методисты.** Внимательная проверка задания с
объяснением — 2–3 мин: ~150–250 заданий за рабочий день на человека.
88 000 заданий ≈ 350–590 человеко-дней; при 6 методистах (2 — математика,
1 — русский язык и чтение, 1–2 — кыргызский язык, 2 — предметы) ≈ 3–5 месяцев.

Поэтапно:

| Этап | Объём | Что проверяем |
|---|---|---|
| 0. Пилот (1–2 недели) | `ort_main_2026` ru, 2 варианта (~400 заданий с запасом) | фактические токены/стоимость, доля `rejected`, время методиста, веса матрицы, константы тайминга, качество промптов |
| 1. Запуск | 10 вариантов на направление (≈ 8 800 заданий) | достаточно для бесплатного первого теста и платных попыток |
| 2. Рост | 30 вариантов на направление | |
| 3. Цель | 100 вариантов на направление (88 000 заданий) | |

После каждого этапа: `review-sync` → `dedup --mark` → `assemble` →
`validate --publish --require-languages` → `import --publish --commit`
(разобрать `cms_conflicts`; варианты, уже бывшие в Firestore, опубликовать в
админке) → `review-sync` → `registry` (коммит обновлённого реестра).

## 6. Известные ограничения

* Message Batches API (−50 % к цене) не используется: запросы идут
  последовательно через streaming. Кандидат на доработку.
* Переводятся только самостоятельные задания; тексты для чтения
  генерируются на каждом языке отдельно.
* Поле `image_path` поддерживается схемой, но этапа загрузки медиа в Storage
  (`exam_media/{questionId}/…`) нет.
* Константы тайминга и веса тем каталога — экспертная оценка до проверки
  методистом и до появления реальных попыток.
* `review-sync`, `export-existing` и `import --commit` работают с реальным
  Firestore и в тестах проверены только через подставной порт (без доступа к
  проекту). Подставной порт, как и Firestore, отклоняет массив внутри массива.
* Правки заданий, сделанные в админке, не переносятся в банк автоматически:
  `import` и `review-sync` только находят их (`cms_conflicts`,
  `translation_links_kept`, `pending_fields` в `cms_caught_up`), перенос —
  вручную.
